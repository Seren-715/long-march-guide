# 《长征路上》Claude / Codex 协作与分支规范

> 生效日：2026-11-17。目的：把**后续提交**按 AI 开发助手分开，保证每次修改可追溯、可测试、可独立审核。
>
> **这份文档不重写既有 Git 提交历史，也不把既有提交强行改写为某个模型所作。** GitHub 上的提交作者可能统一显示仓库所有者，不能仅靠 author/committer 认定真实执行工具。

## 1. 分支归类（检查于 2026-11-17）

| 分支 | 角色 | 处理约定 |
| --- | --- | --- |
| `main` | 稳定集成/发布基线 | 只接收经审核和回归的成果；Claude、Codex 不得直接提交 |
| `claude/design-on-14nodes` | **Claude 专属日常开发**（现存分支） | Claude 新工作提交到此分支，保留已有提交，不重建/强推 |
| `codex/workspace` | **Codex 专属日常开发**（本次创建） | Codex 新工作只提交到此分支，初始代码与分流时 Claude 分支相同 |
| `fix/fujian-evidence-chain-20261116` | 既有修复／PR #2 | 原样保留，仍按 PR #2 审查；不要直接把历史提交都归到 Codex |
| `content/fujian-long-march-stories-20261116` | 既有内容／PR #1 | 原样保留，合并前核对与现有故事分支的重复内容 |
| `content/long-march-story-collection-20261116` | 既有故事资料分支 | 已有工作可能被新版分支继承；历史归属未核实，不重复整批合并 |
| `claude/festive-tesla-cktuym` | 旧 Claude 命名分支 | 历史参考；不再作为日常提交目标 |
| `content/knowledge-additions`、`content/new-node-knowledge`、`content/people-profiles`、`fix/map-route-groups` | 其他历史分支 | 保留存档，逐项比较后再决定是否补入；不得仅按名称归属某个 AI |

**共同基线解释：** Codex 分支从 Claude 最新工作快照分出，故 Codex 分支的 Git 历史会包含分流之前的共同祖先提交。这是正常的；**只有从本次分流点之后各自分支新增的提交才算各自独立开发记录**。禁止为了使历史“看起来纯净”而重写已有提交、改 author、强制推送或强行 cherry-pick。

## 2. 唯一提交目的地

- **Claude**：`claude/design-on-14nodes`
- **Codex**：`codex/workspace`
- **维护者/合并审核**：`main`（必须经用户明确批准）
- 历史 PR #1、#2 的分支不再承接新功能开发；修复 PR 所需的补丁必须单独确认归属与审核流程。
- 一次任务只能在自己的开发分支修改并推送。**不允许将对方分支当作提交目标**，不直接提交 `main`，不擅自合并 PR、部署或修改分支保护规则。
- 开始任务前必须检查当前分支和最新远端状态；如果不是自己的分支，先切换。工作区有未提交修改时先停止并核对，不能覆盖他人工作。

### Claude 开始任务

```bash
git fetch origin
git switch claude/design-on-14nodes
git pull --ff-only origin claude/design-on-14nodes
git status --short
# 修改 / 测试 / 按需提交
git push origin HEAD:claude/design-on-14nodes
```

### Codex 开始任务

```bash
git fetch origin
git switch codex/workspace
git pull --ff-only origin codex/workspace
git status --short
# 修改 / 测试 / 按需提交
git push origin HEAD:codex/workspace
```

GitHub 网页端/连接器操作同理：所有读写调用都显式填写目标分支；如果没有本地 Git，不应默认将代码写到 `main`。

## 3. 工作范围与共享接口

为了降低并行修改冲突，优先按以下**主责**分工（不是绝对文件所有权）：

| Claude 主责 | Codex 主责 |
| --- | --- |
| 首页及故事阅读交互、叙事节奏、人物和地图交互联动、可访问性 | Agent 编排、检索、工具契约、引用/事实规则、联网调用安全性 |
| `src/page.html`、`src/story-guides.js`、`src/story-long.js`、故事展示文案 | `src/server.js`、`scripts/eval-retrieval.mjs`、服务端及回归测试 |
| 故事内容的资料整理与待复核标记（原始史实需核对） | Agent 的回归和对照评测、输入输出校验 |

共享/容易冲突：`src/stories.js`、`src/data.js`、`src/fujian-stories.js`、`scripts/generate.mjs`、`test.mjs`、`worker/index.js`、`README.md`。

涉及共享文件、API 响应结构、工具名、故事 ID 或需要另一方配合时：
1. 先在本分支记录所需契约（字段、输入输出、兼容性及测试）。
2. 告知维护者与另一方；如本轮必须修改共享文件，只在**自己的**分支提交并标明可能冲突的文件。
3. 另一方可参考契约自行实施；不得在未获批准时直接切换、覆写或合入对方工作。
4. `worker/index.js` 是构建产物时，检查生成脚本；不要只改产物而忘记源文件。

## 4. 提交与交接要求

- 提交题目建议：`feat(story): ...`、`feat(agent): ...`、`fix(evidence): ...`、`test(agent): ...`、`docs(collab): ...`。
- 提交说明写清**为什么改、改了什么、影响范围、已运行的测试、仍有哪些限制**；不能把模拟模型测试写成真实 DeepSeek 测试。
- 若确实由对应助手执行，可在提交正文附 `Assistant-Lane: claude` 或 `Assistant-Lane: codex`。这只是协作标记，**不得伪造过去提交的作者身份**。
- 每次提交后向用户报告：分支、完整 HEAD SHA、文件清单、测试结果、风险。不要默认打开 PR 或合并。
- 史实新增或扩写必须提供出处并说明审核状态；网络搜索结果不自动等于已审核史料。
- 禁止提交 API Key、凭据、用户隐私、临时大文件；禁止破坏其他分支、重写已发布历史或未经同意 force push。

## 5. 集成流程（仅在用户明确安排时）

1. 分别检查 Claude、Codex 分支相对 `main` 的差异、共同祖先与重复改动，尤其是共享文件。
2. 由维护者决定具体采用哪些提交或文件改动，在**专门的集成 PR** 中解决冲突，而非直接在两条工作分支交叉合并。
3. 至少运行 `npm test`、`npm run eval:retrieval`、`npm run build`、`node scripts/validate-artifact.mjs`；视变更范围补 Worker/浏览器与真实模型验证。
4. 完成代码审查后，再由用户批准合并到 `main`；部署及比赛提交单独验收。
5. PR #1、#2 **仍是独立历史工作**，不得因新分支建立便视为已合并或自动关闭。

- Codex：请先阅读根目录 `AGENTS.md` 和本文档，确认分支为 `codex/workspace`，仅在本分支提交。
- 若用户明确指定另一工作分支或需要从对方同步成果，应先说明差异与风险、获得明确同意；不能自行修改另一方分支。
